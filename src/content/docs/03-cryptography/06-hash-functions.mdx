> **一句话结论：** 哈希函数是区块链的「指纹机器」，将任意数据压缩成固定长度的唯一标识；以太坊采用 Keccak-256（抗长度扩展攻击）而比特币用 SHA-256（硬件优化），两者虽然名字接近，但构造方法和安全特性完全不同，混用会导致地址生成失败。

## 为什么手机也能验证一个 10GB 的大文件

你是否注意过，从互联网下载一个 Linux ISO（几GB 大小）后，往往会看到一串数字或字母的「校验值」？例如：

```
SHA-256: d9b3e5c2a1f7...（64 个十六进制字符）
```

只需对比这个字符串，就能瞬间检验文件是否被篡改或损坏。这背后的魔法就是**哈希函数**。

区块链用同样的原理：每个区块、每笔交易、每个账户都用哈希函数生成一个「指纹」。这个指纹有三个神奇特性：
1. **确定性**：同样的输入永远生成同样的输出
2. **单向性**：不可能从输出反推输入
3. **雪崩效应**：输入改一个字符，输出也会彻底改变

但这还不够。区块链对哈希函数有额外的严苛要求——特别是**抗碰撞能力**（两个不同输入不能生成同样输出）和**长度扩展攻击防护**。正因为这些要求，以太坊没有跟随比特币选择 SHA-256，而是改用 Keccak-256。

**核心差异表：**

| 特性 | SHA-256 | Keccak-256 |
|------|---------|-----------|
| **使用链** | 比特币、BCH 等 | 以太坊及 EVM 兼容链 |
| **构造方法** | Merkle–Damgård | 海绵（Sponge） |
| **输出长度** | 固定 256 位 | 灵活（可输出任意长度） |
| **长度扩展攻击** | 易受影响（需额外防护） | 原生抵抗 |
| **硬件优化** | 极优（挖矿友好） | 良好（多硬件支持） |
| **并行处理** | 差 | 支持 |
| **NIST 标准** | SHA-2 家族（2001） | 原始 Keccak（2015 改版为 SHA-3，但以太坊仍用旧版） |

### 为什么以太坊不用 SHA-256

**长度扩展攻击（Length Extension Attack）**是关键。想象一个支付场景：你发送了一条消息 `"pay 10 ETH to Alice"`，并用 SHA-256(私钥 + 消息) 生成签名。攻击者无法改动消息本身（因为需要私钥），但在 SHA-256 的 Merkle–Damgård 构造下，**攻击者可以在不知道私钥的情况下，计算出 SHA-256(私钥 + 消息 + 恶意后缀) 的哈希值**。这就悄无声息地改变了交易意图。

Keccak-256 采用的**海绵构造（Sponge Construction）**天然免疫这类攻击。此外，Keccak 的原始设计比 SHA-256 更年轻，在密码分析上也有更多的超前思考。

### 以太坊采用原始 Keccak 的历史遗留

2015 年，NIST 正式发布 SHA-3 标准时，对 Keccak 的填充方案（padding）做了轻微调整以提高灵活性。但以太坊在此之前已经采用了原始 Keccak-256，上线后就一直沿用至今。这样做的好处是保持稳定性；缺点是造成了混淆——有些文档会说以太坊用 SHA-3，但实际是用原始 Keccak，两者生成的哈希值完全不同。

## 在以太坊中的三个核心用途

**1. 生成账户地址：** 对公钥调用 Keccak-256，再取最后 20 字节 = 40 个十六进制字符的以太坊地址

**2. 交易哈希：** 对整个交易数据（gas price、nonce、to 地址等）调用 Keccak-256，得到 txHash，永久记录在区块链上

**3. 状态树节点：** 以太坊的账户状态存储在 Merkle Patricia 树中，每个节点的哈希也是用 Keccak-256 计算，这样轻节点可以快速验证任意账户余额

## 🧪 虚荣地址陷阱：Wintermute 的 $1.6 亿教训

2022 年 9 月，量化做市商 Wintermute 因使用了一个名叫 Profanity 的虚荣地址生成工具，损失了 $1.6 亿美元。

**发生了什么：** Profanity 可以生成看起来「漂亮」的地址，例如 `0x000000...` 开头。但其**致命缺陷是仅用 32 位伪随机数作为种子**，而不是加密级别的强随机数。攻击者用现代 GPU 在几小时内就能暴力枚举 2³²（约 40 亿）个可能的种子值，最终重建出热钱包的私钥。

**教训：** 追求地址美观性（虚荣前缀）会严重妥协安全性。熵不足（32 位 vs 理想的 256 位）在现代计算力面前不堪一击。任何涉及密钥生成的工具，都必须用**加密级伪随机数生成器**（如 `crypto.getRandomValues()` 或 OS 的 `/dev/urandom`），而不是通用随机函数。

## ⚠️ 常见坑与误区

**坑 1：混淆 Keccak-256 和 SHA3-256**
以太坊官方代码中的 `keccak256()` 函数用的是原始 Keccak，不是 NIST 标准化的 SHA3-256。两者哈希值完全不同。如果你从其他库（如 Python 的 hashlib）调用 SHA3-256 并试图匹配以太坊地址生成，会失败。

**坑 2：在哈希之前改变数据编码**
生成地址时，必须对公钥的**二进制数据**（20 字节）调用 Keccak-256，而不是对十六进制字符串哈希。如果误用了字符串编码，结果完全不同。

**坑 3：硬件钱包的盲签名**
硬件钱包屏幕显示「交易哈希」时，用户看到的是一个 64 字符的十六进制串。这个哈希是对交易数据的 Keccak-256 计算结果，但它只代表「这笔交易的指纹」，无法让用户验证**真实的转账目标地址**。攻击者可能篡改了交易的 to 地址，而哈希值看起来完全正常。这就是所谓的「盲签名」风险。

**坑 4：认为哈希值可以逆向**
有些新手期望能从地址反推公钥、从公钥反推私钥。Keccak-256 的单向性意味着这**在数学上不可能**。这也是为什么地址泄露不等于私钥泄露。

## 本节要点

- 哈希函数的三大性质：确定性、单向性、雪崩效应
- SHA-256（比特币）vs Keccak-256（以太坊）的核心差异在于**构造方法**（Merkle–Damgård vs 海绵）和**长度扩展攻击防护**
- 以太坊用 Keccak-256 是因为它在多硬件上更均衡，且原生抵抗长度扩展攻击
- 虚荣地址工具必须用加密级强随机数（≥256 位熵），32 位伪随机数对现代 GPU 完全无防御能力
- Keccak-256 ≠ SHA3-256；混用会导致地址生成失败
- 硬件钱包的盲签名风险无法完全消除，需要在交易前用区块浏览器的「Decode Input Data」人工验证
