> **一句話結論：** 核查專案時，不能只看審計報告；需要用清單逐項驗證融資背景、代幣解鎖計劃、許可權配置和歷史風險，因為大多數DeFi損失實際上來自審計範圍之外的漏洞。

## 為什麼要講這個

想像你去買二手車。經銷商給了一份4S店的檢測報告，說發動機、變速箱都沒問題。你興高采烈地交錢。但其實那份報告沒檢查過：這輛車有幾次重大事故、貸款還清沒有、前任車主是否拖欠罰單。結果買回來三個月，突然出現大問題。

Web3 專案研究也是這樣。審計報告就像那份檢測報告——看起來權威，但覆蓋範圍有限。更關鍵的問題來自你沒檢查的地方：融資方背景是否清白、代幣何時大量解鎖會不會砸盤、專案掌權人是不是集中在少數人手裡。

2026年上半年的統計資料觸目驚心：68個已審計的DeFi協議遭到攻擊，其中46個（67.6%）的攻擊向量完全不在審計覆蓋範圍內，這46個專案的損失高達$680.97 million，佔所有DeFi損失的94.4%。換句話說，通過審計本身幾乎無法保證安全。

## 融資背景核實

融資資訊反映了專案早期的訊號和可信度。你需要驗證四個維度。

**輪次與融資方身份**。看專案融過幾輪、每輪融資額和對應的投資方。知名VC背後通常有盡調團隊，但不是絕對保證。關鍵是看投資方是否有利益衝突——比如同一家VC投了你和你的競爭對手。你可以在Crunchbase、Messari或專案官方公告中核實這些資訊。

**融資距今時間**。最後融資距離現在多遠很重要。如果一個專案上次融資是兩年前，而同領域專案還在活躍募資，說明融資環境對它不友好。反過來，剛融資的專案通常意味著投資方對其近期前景有信心，但也要警惕高估值融資後產品迭代跟不上的風險。

**資金用途追蹤**。部分專案會披露融資資金的使用計劃。理想情況下，融資用於研發和市場，而非單純分配給創始人。你可以通過鏈上資料（DefiLlama的財務指標）或官方披露檔案追蹤當前跑速。

| 融資資訊 | 檢查內容 | 資料來源 |
|--------|--------|--------|
| **輪次** | A/B/C/D 輪，融資額 | Crunchbase、官方公告 |
| **投資方** | 知名VC、戰略投資者背景 | LinkedIn、Messari |
| **時間** | 最後融資距今，融資間隔 | 官方網站、新聞稿 |
| **一致性** | 公開融資資訊 vs 鏈上資金流向 | Dune、DefiLlama、錢包鏈上追蹤 |

## 代幣鎖倉與解鎖時間表

代幣解鎖是能精確預測的風險因素。不少專案因大額解鎖而崩盤，這完全可以提前規避。

**初始流通比例**。專案代幣中，有多少已經釋放給市場？流通量越低，解鎖壓力越大。一般來說，初始流通比例超過30%的專案風險較低；低於10%的專案需要特別關注。

**Vesting 時間表**。大多數專案採用"1年cliff + 3年線性釋放"的標準模式——意思是第一年代幣鎖定不動，之後每個月釋放四分之一。你需要找到具體的解鎖曲線，標記關鍵時間點。特別要留意"TGE（代幣生成事件）當天解鎖超過25%"的專案——歷史資料顯示，這類專案首年平均價跌72%。

**大額解鎖日期的風險**。假設專案有一次大的cliff結束或投資輪解鎖，需要提前2-4周開始監控市場情緒。用Dune或Token Unlock這樣的工具繪製解鎖曲線，與歷史價格對應，看市場通常怎麼反應。

**團隊與投資方持倉比例**。如果團隊持有超過50%的代幣且都在3年內解鎖，這是紅旗。相反，如果投資方持倉分散、解鎖週期長，說明專案方信心足、不急著套現。

## 審計報告真假驗證

審計是必要的安全卡位，但不是充分條件。你需要核查三層資訊。

**審計方信譽**。2026年主流的頂級審計公司包括OpenZeppelin、Trail of Bits、ChainSecurity、Spearbit。這些機構有嚴格的標準化流程和公開的歷史記錄。如果一個專案選擇了不知名的小公司審計，或者根本沒有通過第三方審計（只是內部自審），這是明顯的紅旗。

**審計覆蓋範圍**。審計報告通常明確說明"Scope"——即它審計的是哪個版本的程式碼、哪些合約、哪些風險類別。關鍵是看審計是否覆蓋了：重入風險、訪問控制漏洞、預言機風險、升級邏輯。但審計永遠不覆蓋：管理員濫用許可權、社交工程、跨協議互動。

**部署程式碼與審計版本一致性**。最常見的陷阱是：專案釋出審計報告後，又修改了程式碼才部署。你需要核實Etherscan上顯示的部署程式碼hash，與審計報告附件中的程式碼hash是否匹配。可以用Tenderly或Etherscan的"Verify Contract"功能對比。

## 🧪 盡職調查實操清單

<Steps>
1. **融資背景查證**：在 Crunchbase / Messari 上查該專案的融資輪次、投資方、融資額；用 Google 搜尋投資方名稱，看是否有過"聯合投資"記錄，確認無利益衝突。

2. **審計報告獲取與驗證**：從專案官網或 GitHub 下載審計報告 PDF，記下審計方名稱、審計範圍（Scope）、發現的漏洞等級；使用 Etherscan 的 "Contract Source Code" 驗證部署程式碼與審計版本的 hash 值是否一致。

3. **代幣解鎖曲線繪製**：訪問 Token Unlock 或 Tokenomist 檢視完整的解鎖時間表；用 Dune SQL 自建儀表板追蹤未來3-6個月的月度解鎖量；標記 cliff 結束日、TGE 日期等關鍵時間點。

4. **升級許可權配置檢查**：在 Etherscan 上查專案的關鍵合約，記錄"Owner"或"Admin"欄位；如果是多籤帳戶，查該多籤的簽署者名單、需要多少簽名才能執行升級（N-of-M）；理想情況是 3-of-5 或 5-of-7 的分散配置；如果是單個錢包地址控制，這是嚴重風險。

5. **歷史安全事件追蹤**：用 Google 搜尋專案名 + "hack" / "exploit"；在 DeFi Sentinel 或 Immunefi 資料庫查是否有歷史漏洞記錄；訪問專案的 GitHub issue，看是否有公開的安全反饋。
</Steps>

## ⚠️ 常見坑與誤區

**坑1：過度相信"已審計"標籤。** 2026年上半年資料明確顯示，68個已審計協議中有46個遭攻擊，損失$680.97 million佔總損失的94.4%，這些攻擊的向量完全在審計覆蓋範圍外——比如管理員許可權濫用、社交工程、預言機操縱。審計報告通常僅覆蓋智能合約程式碼邏輯，不覆蓋運維風險和人類因素。不要把審計當做"安全證明"，只能當做"必要門檻"。

**坑2：忽視管理員許可權的集中化風險。** Drift Protocol在2026年4月遭遇$285 million駭客攻擊，根本原因是攻擊者通過社交工程獲取了安全委員會成員的金鑰，這完全規避了合約審計。如果專案的管理員許可權集中在少數人手裡，或者使用單籤而非多籤，風險極高。必須檢查專案的多籤配置是否為N-of-M的分散結構。

**坑3：基礎設施中心化導致的風險。** Kelp DAO在2026年4月失去$292 million，表面看是智能合約漏洞，實際是攻擊者入侵了Kelp採用的單一RPC節點（1-of-1驗證器配置），注入偽造的跨鏈訊息。這說明即使合約本身正確，基礎設施的中心化依賴也能導致災難。要檢查專案是否依賴單一RPC提供商或單個驗證器。

**坑4：代幣解鎖時間表分析不足。** 看到初始流通量就下結論是常見錯誤。Polkadot、Filecoin等大專案都有4-6年的長期解鎖計劃，但大額解鎖日期是明確的風險事件。如果不把這個時間表納入評估，就容易被市場中的解鎖潮殺個措手不及。

**坑5：投資方背景調查草率。** "有知名VC投資"不代表專案沒風險。需要查這家VC的投資組合是否有過失敗案例、是否與專案有利益衝突、融資後的市場環境是否有變化。有些VC投的專案後來跑路了，這是公開資訊，不做背景調查就容易踩坑。

## 本節要點

- 審計報告只是必要非充分條件，不要盲目相信"已審計"標籤，需要查審計範圍、審計方信譽和部署程式碼一致性。
- 融資背景（輪次、投資方、融資距今時間）是早期風險訊號，可通過Crunchbase和官方公告核實。
- 代幣解鎖時間表是能精確預測的風險因素，初始流通比&lt;10%或TGE當天解鎖>25%的專案歷史上容易大幅下跌。
- 升級許可權配置至關重要，需要檢查是否為多籤（3-of-5或以上）而非單個錢包控制，單籤是嚴重紅旗。
- 基礎設施風險（RPC依賴、驗證器集中度）往往被忽視，但可能導致與合約程式碼漏洞同等規模的損失。
- 用Dune、Token Unlock、Etherscan、Tenderly等工具跨平臺交叉驗證，不要依賴單一資料來源。
