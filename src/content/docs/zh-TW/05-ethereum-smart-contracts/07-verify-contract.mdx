> **一句話結論：** "驗證（Verified）不等於安全（Safe），它只是公開了程式碼，你還需要用紅旗清單快速掃一遍常見後門函式。"

## 為什麼這一步這麼重要

想像你走進一家陌生的便利店，看到店內攝像頭對著收銀臺（這就是「驗證」）。攝像頭證明了操作是被記錄的、透明的，但這不代表老闆不會偷偷改價格、或者收銀系統裡有木馬。你還得看一下價目表、問問有沒有隱藏費用。

以太坊合約也一樣。當你看到 Etherscan 上一個綠色的"✓ Contract Verified"時，確實意味著程式碼是公開的，但：
- ✅ 程式碼透明瞭
- ❌ 程式碼邏輯可能有意隱藏的後門
- ❌ 可升級合約（Proxy）隨時可能被改寫

真實案例：2017 年，Parity 多簽名錢包的驗證程式碼看起來很正常，但裡面藏著一個 `delegatecall` 漏洞，最終導致 1.52 億美元的資金被凍結。如果使用者當時知道查"紅旗函式"，就能及時躲避。

## 從原始碼到鏈上位元組碼：驗證的三種方式

Etherscan、Sourcify、Blockscout 都能做驗證，原理都是：**上傳原始碼 → 用同一個編譯器重新編譯 → 對比位元組碼是否一致**。

| 驗證工具 | 支援鏈 | 使用難度 | 透明度 | 適用場景 |
|---------|-------|--------|-------|--------|
| **Etherscan** | Ethereum、Polygon 等 | 易（Web UI） | 中（中心化） | 大多數專案，最常見 |
| **Sourcify** | 所有 EVM 鏈 | 中（去中心化）| 高（開源） | 追求透明性的專案 |
| **Blockscout** | 任何 EVM 鏈 | 中（自部署） | 高（開源）| 私有或小眾鏈 |

**關鍵點**：驗證時需要提供的資訊包括 Solidity 版本號、最佳化設定、具體編譯引數。開發者故意提交錯誤的引數，編譯出的位元組碼會不一致，驗證就會失敗。這個機制防止了"我驗證了我的程式碼"而實際鏈上程式碼不同的欺騙。

但這裡有個陷阱：如果專案用的是 **Proxy Pattern（代理模式）**，使用者看到的"驗證"其實只是代理合約本身驗證了，真正的邏輯合約（Implementation）可能未驗證，甚至故意隱藏。專案方可以在使用者不知情下升級邏輯，注入後門。

## 紅旗清單：30 秒快速識別後門函式

拿到驗證的原始碼後，不需要全讀一遍。用 Ctrl+F 搜尋這些關鍵詞，看看有沒有危險的許可權模式。

**常見後門函式速查表**：

| 函式名 | 危險指標 | 為什麼危險 | 如何檢查 |
|--------|--------|----------|--------|
| `mint()` `burn()` | 有就是綠旗 ✅ | 正常，專案需要鑄幣權 | 搜 `mint`，檢查是否有 `onlyOwner` 或 `onlyMinter` |
| `setFees()` `setTaxes()` | Owner 可調 | Owner 可把稅改成 100%，變成黑洞 | 搜 `setFee`，檢查是否有許可權檢查和上限 |
| `blacklist()` `ban()` | Owner 可調 | Owner 可凍結任何地址的轉帳 | 搜 `blacklist`，看有無許可權限制 |
| `pause()` | Owner 可調 | Owner 可凍結全網交易 | 搜 `pause`，最好有 timelock（延遲） |
| `emergencyWithdraw()` | 無許可權檢查 | Owner 可直接提走使用者存款 | 搜函式，看是否能提走他人資金 |
| `delegatecall` 到動態地址 | 任意一個都是 🔴 | 任意程式碼執行，直接淪陷 | 搜 `delegatecall`，必須指向固定信任合約 |
| `upgradeTo()` 單個管理員 | 單個 EOA | 管理員私鑰洩露 = 專案淪陷 | 查誰有升級權，最好是多籤錢包 |

**真實傷害案例**（2024-2026）：超過 50% 的 rug pull 專案都是通過改 setFees 或 mint 許可權來割韭菜的。

## 🧪 實操：30 秒快速核驗一個合約

<Steps>

1. **開啟 Etherscan，找到合約地址**
   - 在搜尋框輸入合約地址（0x... 的 42 位地址）
   - 如果不確定地址，可從 DEXTools、CoinGecko 上抄

2. **檢查是否已驗證**
   - 進入 Contract 標籤
   - 看是否顯示"✓ Contract Verified"綠色標記
   - 如果顯示 Unverified，立即關閉，別碰

3. **讀原始碼，搜尋紅旗函式**
   - 點"Code"，看完整原始碼
   - Ctrl+F 搜尋：`mint` `setFee` `pause` `blacklist` `delegatecall` `upgradeTo`
   - 每找到一個，看是否有 `onlyOwner` 或類似許可權檢查

4. **檢查管理員身份**
   - 搜尋 `owner` 或 `admin`
   - 看管理員是 EOA（單個地址，極其危險）還是多籤錢包（相對安全）
   - 可點選地址，用 Etherscan 查該地址是否有異常交易歷史

5. **檢視合約是否可升級**
   - 如果看到 `delegatecall` 且指向另一個地址的合約，就是代理模式
   - Etherscan 會自動標記"Proxy"
   - 點選 Implementation 地址，查實現合約是否也已驗證
   - 如果未驗證，存在隱藏後門的風險，建議避開

6. **做最後判斷**
   - 🟢 **綠燈**：已驗證 + 常見紅旗函式都有許可權檢查 + 管理員是多籤或 DAO
   - 🟡 **黃燈**：已驗證但有單一 Owner + 沒有 timelock + 升級權不透明
   - 🔴 **紅燈**：未驗證、Proxy 的 Implementation 未驗證、delegatecall 到動態地址、無許可權檢查

</Steps>

## ⚠️ 常見坑與誤區

1. **"看到綠色對勾就放心了"** ❌
   - 很多專案在審計階段提交乾淨程式碼給 Etherscan，驗證通過了。但之後通過升級合約注入後門。使用者沒有方式察覺，因為 Etherscan 顯示的還是原來"驗證通過"的程式碼。
   - 真實案例：某 DeFi 專案 2024 年上線時驗證程式碼乾淨無比，但 3 個月後通過 Proxy 升級，改了 setFees 許可權，抽走 2000 萬美元。

2. **"Proxy Pattern 的專案都不可信"** ❌
   - 錯。Compound、Uniswap 等龍頭都用 Proxy。關鍵看誰控制升級權。
   - 透明的升級（多籤+公示期+歷史記錄公開）就是安全的。
   - 風險在於單個人、單個帳戶擁有升級權，或者根本沒有公示、不透明升級。

3. **"我不看程式碼，只看社群怎麼說"** ❌
   - 社群往往盲目樂觀。參考 The DAO 攻擊前，社群一致看好。
   - 後門往往隱藏在看似無害的函數里，只有主動查程式碼才能發現。

4. **"合約地址寫錯了一個字元，也能查"** ❌
   - 以太坊地址有內建校驗碼，錯一個字元會導致地址無效。
   - 但騙子常用"相似地址"（比如 0x123abc... 和 0x123abd...），視覺上只差一個字母。
   - 核驗前一定要對標官方渠道的地址，或用 Etherscan 連結而不是手抄。

5. **"最佳化（Optimization）設定不一樣，就是不同的程式碼"** ⚠️
   - 編譯器最佳化只改位元組碼的排列，不改邏輯。
   - 但如果開發者上傳驗證時說"最佳化 enabled"，實際編譯是"disabled"，驗證會失敗。
   - 所以驗證失敗可能真的意味著程式碼被篡改，也可能就是提交資訊有誤。關鍵看專案方如何解釋。

## 本節要點

- **驗證 = 程式碼透明，不 = 程式碼安全。** 驗證只是審計的前置條件，不是審計本身。
- **紅旗函式不是都是後門。** `mint` `pause` 等許可權函式本身正常，關鍵看有沒有許可權檢查和上限。
- **Proxy Pattern 本身不可怕，可怕的是升級權管理。** 多籤或 DAO 治理的升級方案是安全的；單個 EOA 完全控制就是雷。
- **實現合約（Implementation）未驗證 = 隱藏後門。** 代理合約再幹淨也沒用，一旦實現合約隱藏，專案方可暗自升級注入後門。
- **delegatecall 到動態地址 = 直接被黑。** 這個函式一旦出現，整個合約淪陷。搜尋程式碼時如果看到，立即關閉。
- **30 秒掃一遍紅旗清單，勝過盲目信任。** 參考本節表格快速檢查，多數 rug pull 專案都能在驗證程式碼階段識別出來。
