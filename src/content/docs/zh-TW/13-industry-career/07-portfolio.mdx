> **一句話結論：** Web3 求職的作品集不需要完美，但需要展示你遇過的真實問題、怎樣分析、為什麼這樣解決。三個能證明"你動過手"的可交付物，比一百頁的 PPT 演講稿更有說服力。

## 為什麼作品集比學歷更重要

招聘方在篩簡歷時，不是在找"讀過最多書的人"，而是找"解決過實際問題的人"。

根據 Consensys 等一線公司 2026 年的招聘資料，他們審查簡歷的流程是這樣的：看你做過什麼（有真實專案嗎）→ 查你的程式碼質量（GitHub、開源貢獻）→ 評估你的學習速度（遇到新問題怎麼解決）。

前兩項都需要作品集來證明。沒有專案經驗不是致命傷，但沒有作品集的話，競爭力會明顯下降。

## 三類可交付物的標準

Web3 行業認可的作品集主要分三類，根據你的崗位方向選擇合適的。

### 1. 程式碼專案（技術崗）

如果你要做技術類崗位（工程、產品、資料分析），GitHub 倉庫是必須的。但這裡有個重要的誤區：**不是說程式碼必須完成度 100%**。

關鍵是能展示你理解的技術深度。比如 GitHub 上這些高 star 的專案：

| 專案名 | 星數 | 代表什麼能力 | 求職價值 |
|-------|------|----------|---------|
| web3.js | 19,900 | 官方庫維護、大規模程式碼管理 | 能維護關鍵基礎設施 |
| ethers.js | 8,700 | 替代方案設計、API 友好性 | 重視使用者體驗的工程師 |
| WTF-Solidity | 14,000 | 教育能力、社群影響力 | 能把複雜概念講清楚 |
| Hey (Lens) | 29,400 | 全棧應用開發、鏈上互動 | 真實的產品化能力 |

你的專案不需要達到這個量級，但應該展示類似的"深度訊號"：有清晰的問題定義、有解決方案、有測試、有文件。

### 2. 鏈上作品（DeFi/安全相關）

- **智能合約審計報告**：評估 3-5 個已釋出的合約，寫出風險分析
- **DAO 治理提案**：在 Snapshot 上撰寫提案，展示對生態的理解
- **DeFi 交易指令碼**：開源套利機器人、流動性監聽器等

價值：證明你研究過鏈上資料和合約程式碼，而不只是紙上談兵。

### 3. 內容與分析報告（非技術崗）

- **社群增長案例**：從 0 到 X 人的過程、用過的策略、資料結果
- **市場分析文章**：發在 Mirror、Dev.to 的深度分析
- **鏈上資料儀表板**：用 Dune 視覺化某個協議的關鍵指標

關鍵：用數字說話，不是"我覺得不錯"，而是"A vs B，資料顯示提升 40%"。

## 🧪 作品集的實操組織

<Steps>

1. **選一個真實的問題**
   - 最好是你用某個產品時發現的坑，或者想驗證的鏈上現象
   - 不要為了作品集而強行創意——真實感最重要

2. **做最小化可行版本（MVP）**
   - 技術類：一個能跑的指令碼或合約，功能不用完整，但程式碼要能看
   - 非技術類：收集 5-10 個有代表性的資料點，而不是 100 頁報告
   - 時間目標：1-2 周完成，不要拖半年

3. **寫清楚 README**
   - **背景**："我發現……，決定造這個"
   - **成果**："採集 20+ 資料來源、準確率 94%"
   - **技術棧** 和**難點突破**（"問題 → 解決方案"）
   - **使用指南**：能跑起來

4. **把過程記錄下來**
   - 每次 commit 都寫清楚幹了什麼（而不是"fix bug"）
   - 遇到問題時在 issue 裡記錄思考過程
   - 最後寫一份反思文件（LEARNINGS.md 或 POST_MORTEM.md）

5. **發出去獲反饋**
   - 在 GitHub 開源，邀請 star 和 issue
   - 在社群論壇或 Twitter 分享（@Ethereum、r/ethdev 等）
   - 投稿到 Dev.to 或 Mirror
   - **讓招聘方能找到你**

</Steps>

## ⚠️ 常見坑與誤區

**坑 1：過度包裝但空心**

程式碼是 copy-paste 的模板，面試一問細節就露餡。避法：程式碼寧可醜，但必須自己理解。

**坑 2：追求"大而全"，永遠做不完**

"我要造個 DeFi 平臺"，結果 2 年還在"開發中"。避法：先完成"小而精"的專案，有真實成果再規劃下一個。

**坑 3：資訊不完整**

README 只有安裝指令，沒有背景和核心邏輯。避法：用一段話說明"為什麼做這個"和"核心創新是什麼"。

**坑 4：做完就扔，不維護**

GitHub 最後提交 8 個月前，說明放棄了。避法：定期看 issue 和 PR，2-3 個月回應一次反饋。

**坑 5：非技術崗放棄作品集**

社群運營或 BD 的人說"沒程式碼就沒作品集"。避法：用 Dune、Notion 做"社群增長報告"或"市場分析"，資料本身就是作品。

## 本節要點

- 作品集不需要完美，需要"有血有肉"：有問題背景、有技術難點、有反思
- 三類可交付物都可以：程式碼專案、鏈上作品、內容報告，根據崗位選擇
- README 比程式碼本身更重要——讓人在 30 秒內理解你做了什麼
- 承認失敗的嘗試與學到的東西，比講"一切順利"更有說服力
- 完成度 70% 的真實專案，比完美的草稿更值錢；把"進行中"改成"已完成"
