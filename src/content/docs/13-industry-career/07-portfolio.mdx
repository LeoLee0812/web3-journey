> **一句话结论：** Web3 求职的作品集不需要完美，但需要展示你遇过的真实问题、怎样分析、为什么这样解决。三个能证明"你动过手"的可交付物，比一百页的 PPT 演讲稿更有说服力。

## 为什么作品集比学历更重要

招聘方在筛简历时，不是在找"读过最多书的人"，而是找"解决过实际问题的人"。

根据 Consensys 等一线公司 2026 年的招聘数据，他们审查简历的流程是这样的：看你做过什么（有真实项目吗）→ 查你的代码质量（GitHub、开源贡献）→ 评估你的学习速度（遇到新问题怎么解决）。

前两项都需要作品集来证明。没有项目经验不是致命伤，但没有作品集的话，竞争力会明显下降。

## 三类可交付物的标准

Web3 行业认可的作品集主要分三类，根据你的岗位方向选择合适的。

### 1. 代码项目（技术岗）

如果你要做技术类岗位（工程、产品、数据分析），GitHub 仓库是必须的。但这里有个重要的误区：**不是说代码必须完成度 100%**。

关键是能展示你理解的技术深度。比如 GitHub 上这些高 star 的项目：

| 项目名 | 星数 | 代表什么能力 | 求职价值 |
|-------|------|----------|---------|
| web3.js | 19,900 | 官方库维护、大规模代码管理 | 能维护关键基础设施 |
| ethers.js | 8,700 | 替代方案设计、API 友好性 | 重视用户体验的工程师 |
| WTF-Solidity | 14,000 | 教育能力、社区影响力 | 能把复杂概念讲清楚 |
| Hey (Lens) | 29,400 | 全栈应用开发、链上交互 | 真实的产品化能力 |

你的项目不需要达到这个量级，但应该展示类似的"深度信号"：有清晰的问题定义、有解决方案、有测试、有文档。

### 2. 链上作品（DeFi/安全相关）

- **智能合约审计报告**：评估 3-5 个已发布的合约，写出风险分析
- **DAO 治理提案**：在 Snapshot 上撰写提案，展示对生态的理解
- **DeFi 交易脚本**：开源套利机器人、流动性监听器等

价值：证明你研究过链上数据和合约代码，而不只是纸上谈兵。

### 3. 内容与分析报告（非技术岗）

- **社区增长案例**：从 0 到 X 人的过程、用过的策略、数据结果
- **市场分析文章**：发在 Mirror、Dev.to 的深度分析
- **链上数据仪表板**：用 Dune 可视化某个协议的关键指标

关键：用数字说话，不是"我觉得不错"，而是"A vs B，数据显示提升 40%"。

## 🧪 作品集的实操组织

<Steps>

1. **选一个真实的问题**
   - 最好是你用某个产品时发现的坑，或者想验证的链上现象
   - 不要为了作品集而强行创意——真实感最重要

2. **做最小化可行版本（MVP）**
   - 技术类：一个能跑的脚本或合约，功能不用完整，但代码要能看
   - 非技术类：收集 5-10 个有代表性的数据点，而不是 100 页报告
   - 时间目标：1-2 周完成，不要拖半年

3. **写清楚 README**
   - **背景**："我发现……，决定造这个"
   - **成果**："采集 20+ 数据源、准确率 94%"
   - **技术栈** 和**难点突破**（"问题 → 解决方案"）
   - **使用指南**：能跑起来

4. **把过程记录下来**
   - 每次 commit 都写清楚干了什么（而不是"fix bug"）
   - 遇到问题时在 issue 里记录思考过程
   - 最后写一份反思文档（LEARNINGS.md 或 POST_MORTEM.md）

5. **发出去获反馈**
   - 在 GitHub 开源，邀请 star 和 issue
   - 在社区论坛或 Twitter 分享（@Ethereum、r/ethdev 等）
   - 投稿到 Dev.to 或 Mirror
   - **让招聘方能找到你**

</Steps>

## ⚠️ 常见坑与误区

**坑 1：过度包装但空心**

代码是 copy-paste 的模板，面试一问细节就露馅。避法：代码宁可丑，但必须自己理解。

**坑 2：追求"大而全"，永远做不完**

"我要造个 DeFi 平台"，结果 2 年还在"开发中"。避法：先完成"小而精"的项目，有真实成果再规划下一个。

**坑 3：信息不完整**

README 只有安装指令，没有背景和核心逻辑。避法：用一段话说明"为什么做这个"和"核心创新是什么"。

**坑 4：做完就扔，不维护**

GitHub 最后提交 8 个月前，说明放弃了。避法：定期看 issue 和 PR，2-3 个月回应一次反馈。

**坑 5：非技术岗放弃作品集**

社区运营或 BD 的人说"没代码就没作品集"。避法：用 Dune、Notion 做"社区增长报告"或"市场分析"，数据本身就是作品。

## 本节要点

- 作品集不需要完美，需要"有血有肉"：有问题背景、有技术难点、有反思
- 三类可交付物都可以：代码项目、链上作品、内容报告，根据岗位选择
- README 比代码本身更重要——让人在 30 秒内理解你做了什么
- 承认失败的尝试与学到的东西，比讲"一切顺利"更有说服力
- 完成度 70% 的真实项目，比完美的草稿更值钱；把"进行中"改成"已完成"
